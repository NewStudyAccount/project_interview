# 分布式事务

## Q1: 分布式事务方案对比？

| 方案 | 一致性 | 性能 | 侵入性 | 适用场景 |
|------|--------|------|--------|----------|
| 2PC | 强一致 | 低 | 低 | 传统数据库 |
| 3PC | 强一致 | 中 | 低 | 学术方案 |
| TCC | 最终一致 | 高 | 高 | 资金业务 |
| Saga | 最终一致 | 高 | 中 | 长事务 |
| 本地消息表 | 最终一致 | 高 | 中 | 异步场景 |
| Seata AT | 最终一致 | 中 | 低 | 通用场景 |

## Q2: Seata AT 模式原理？

```
┌──────────────────────────────────────────────────────────┐
│              Seata AT 模式原理                            │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  组件:                                                   │
│  ├── TC (Transaction Coordinator): 事务协调器             │
│  ├── TM (Transaction Manager): 事务发起者                │
│  └── RM (Resource Manager): 资源管理者 (分支事务)        │
│                                                          │
│  流程:                                                   │
│  1. TM 向 TC 申请开启全局事务 → 生成 XID                │
│  2. XID 在微服务调用链中传播                             │
│  3. RM 向 TC 注册分支事务                               │
│  4. RM 执行本地事务:                                    │
│     ├── 解析 SQL, 记录 before image                     │
│     ├── 执行 SQL                                        │
│     ├── 记录 after image                                │
│     └── 生成 undo log, 提交本地事务                     │
│  5. 全部成功 → TM 通知 TC 提交 → TC 删除 undo log       │
│  6. 某个失败 → TM 通知 TC 回滚 → TC 根据 undo log 回滚  │
│                                                          │
│  undo log 结构:                                          │
│  ┌─────────────────────────────────────────────────┐     │
│  │  before image: 执行前的数据快照                  │     │
│  │  after image:  执行后的数据快照                  │     │
│  │  行锁: 用于回滚时的并发控制                     │     │
│  └─────────────────────────────────────────────────┘     │
│                                                          │
│  回滚: 反向补偿                                         │
│  ├── INSERT → DELETE                                    │
│  ├── DELETE → INSERT                                    │
│  └── UPDATE → UPDATE (用 before image)                  │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### Seata 使用示例

```java
// 1. TM 发起全局事务
@Service
public class OrderService {

    @GlobalTransactional(timeoutMills = 60000, name = "create-order")
    public void createOrder(OrderDTO orderDTO) {
        // 1. 创建订单
        orderMapper.insert(order);
        // 2. 扣减库存 (远程调用)
        stockClient.deductStock(orderDTO.getSkuId(), orderDTO.getCount());
        // 3. 扣减余额 (远程调用)
        accountClient.deductBalance(orderDTO.getUserId(), orderDTO.getTotalAmount());
    }
}

// 2. RM 分支事务
@Service
public class StockService {

    @Transactional
    public void deductStock(Long skuId, Integer count) {
        // 本地事务，Seata 自动代理
        stockMapper.deductStock(skuId, count);
    }
}
```

## Q3: TCC 模式原理？

```
┌──────────────────────────────────────────────────────────┐
│              TCC 模式原理                                 │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  Try: 预留资源 (冻结)                                    │
│  ├── 检查业务可行性                                      │
│  ├── 预留必需的资源                                      │
│  └── 例如: 冻结库存、冻结余额                            │
│                                                          │
│  Confirm: 确认提交                                       │
│  ├── 使用 Try 阶段预留的资源                             │
│  ├── 幂等操作                                            │
│  └── 例如: 扣减冻结库存、扣减冻结余额                    │
│                                                          │
│  Cancel: 取消回滚                                        │
│  ├── 释放 Try 阶段预留的资源                             │
│  ├── 幂等操作                                            │
│  └── 例如: 解冻库存、解冻余额                            │
│                                                          │
│  示例: 订单创建                                          │
│  ┌─────────────────────────────────────────────────┐     │
│  │  Try:                                            │     │
│  │    库存: frozen_count += count (冻结)            │     │
│  │    余额: frozen_amount += amount (冻结)          │     │
│  │                                                  │     │
│  │  Confirm:                                        │     │
│  │    库存: stock -= count, frozen_count -= count   │     │
│  │    余额: balance -= amount, frozen_amount -= amt │     │
│  │                                                  │     │
│  │  Cancel:                                         │     │
│  │    库存: frozen_count -= count (解冻)            │     │
│  │    余额: frozen_amount -= amount (解冻)          │     │
│  └─────────────────────────────────────────────────┘     │
│                                                          │
│  优点: 性能高, 不锁数据库资源                            │
│  缺点: 业务侵入大, 需要实现三个接口                      │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

## Q4: Saga 模式原理？

```
┌──────────────────────────────────────────────────────────┐
│              Saga 模式原理                                │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  长事务拆分为多个本地事务:                               │
│                                                          │
│  T1 → T2 → T3 → T4 → ... → Tn                          │
│                                                          │
│  每个 Ti 有对应的补偿 Ci:                                │
│                                                          │
│  正常: T1 → T2 → T3 → T4                                │
│                                                          │
│  T3 失败: T3 → C2 → C1                                  │
│  (逆向补偿)                                              │
│                                                          │
│  实现方式:                                               │
│  ├── 编排式 (Choreography): 事件驱动, 无中心协调器      │
│  │   └── 每个服务监听事件, 执行本地事务后发布事件       │
│  └── 编排式 (Orchestration): 中心协调器                  │
│      └── 协调器按顺序调用各服务                          │
│                                                          │
│  Seata Saga:                                             │
│  ├── 基于状态机引擎                                     │
│  ├── JSON 定义流程                                      │
│  └── 支持嵌套事务                                       │
│                                                          │
│  适用场景:                                               │
│  ├── 长流程业务 (跨多个服务)                             │
│  ├── 第三方接口 (无法做 TCC)                             │
│  └── 补偿逻辑明确的业务                                  │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

## Q5: 本地消息表方案？

```
┌──────────────────────────────────────────────────────────┐
│              本地消息表方案                                │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  核心思想: 本地事务 + 消息表 + 消息队列                  │
│                                                          │
│  流程:                                                   │
│  1. 业务操作和消息写入在同一个事务中                     │
│     BEGIN;                                              │
│       INSERT INTO orders ...;                           │
│       INSERT INTO outbox_messages (status='PENDING');   │
│     COMMIT;                                             │
│                                                          │
│  2. 定时任务扫描消息表，发送到 MQ                       │
│     SELECT * FROM outbox_messages WHERE status='PENDING'│
│     → 发送到 RabbitMQ/Kafka                             │
│     → 更新状态为 'SENT'                                 │
│                                                          │
│  3. 消费者处理消息                                       │
│     → 处理业务 (幂等)                                   │
│     → ACK 消息                                          │
│                                                          │
│  4. 定时任务重试未确认的消息                             │
│                                                          │
│  ┌─────────┐  本地事务  ┌─────────┐                     │
│  │ 业务表   │◀─────────▶│ 消息表  │                     │
│  └─────────┘           └────┬────┘                     │
│                             │                           │
│                      定时扫描│发送                       │
│                             ▼                           │
│                       ┌─────────┐                       │
│                       │  MQ     │                       │
│                       └────┬────┘                       │
│                            │                            │
│                            ▼                            │
│                       ┌─────────┐                       │
│                       │ 消费者   │                       │
│                       └─────────┘                       │
│                                                          │
│  优点: 实现简单, 不依赖特定框架                          │
│  缺点: 侵入业务, 需要维护消息表                          │
│                                                          │
└──────────────────────────────────────────────────────────┘
```
