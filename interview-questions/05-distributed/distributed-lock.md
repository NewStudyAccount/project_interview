# 分布式锁

## Q1: 为什么需要分布式锁？本地锁为什么不够？

| 维度 | 本地锁 (synchronized / ReentrantLock) | 分布式锁 |
|------|--------------------------------------|----------|
| 作用范围 | 单 JVM 进程内 | 跨进程 / 跨机器 |
| 适用场景 | 单实例应用 | 多实例部署、微服务集群 |
| 实现 | JVM 内存对象 | 外部共享存储 (Redis / ZK / DB) |
| 性能 | 极高 (纳秒级) | 相对低 (网络 RTT) |
| 可靠性 | 进程退出即释放 | 依赖存储组件的高可用 |

### 为什么集群下本地锁会失效？

```
┌──────────────────────────────────────────────────────────┐
│              多实例下的并发问题                            │
├──────────────────────────────────────────────────────────┤
│                                                          │
│   Client 请求                                             │
│      │                                                   │
│      ▼                                                   │
│   ┌──────────┐     ┌──────────┐     ┌──────────┐        │
│   │ 服务 A   │     │ 服务 B   │     │ 服务 C   │        │
│   │ lock()   │     │ lock()   │     │ lock()   │        │
│   │ (本地锁) │     │ (本地锁) │     │ (本地锁) │        │
│   └────┬─────┘     └────┬─────┘     └────┬─────┘        │
│        │                │                │               │
│        ▼                ▼                ▼               │
│   ┌──────────────────────────────────────────┐          │
│   │              同一 MySQL / 库存           │          │
│   │         三个实例同时操作同一资源          │          │
│   │              本地锁完全无效               │          │
│   └──────────────────────────────────────────┘          │
│                                                          │
│  典型场景:                                               │
│  ├── 库存扣减: 超卖                                      │
│  ├── 订单号生成: 重复单号                                │
│  ├── 定时任务: 多实例重复执行                            │
│  └── 优惠券领取: 超发                                    │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 分布式锁的三个核心诉求

| 诉求 | 含义 |
|------|------|
| **互斥** | 同一时刻只有一个客户端持有锁 |
| **防死锁** | 持有者崩溃后锁能自动释放（超时 / 临时节点） |
| **解铃还须系铃人** | 只有加锁者能解锁（唯一标识 + Lua 原子校验） |

### 面试答法

> "分布式锁解决的是多进程/多实例并发操作共享资源的问题。本地锁只能锁单个 JVM，集群部署后每个实例一把锁，完全互斥不了。常见场景是秒杀库存、定时任务防重复、优惠券防超发。分布式锁要求互斥、防死锁、只有持有者能释放。"

## Q2: Redis 分布式锁实现？SETNX + 过期时间 + 唯一值？（高频）

### 基本实现

```
┌──────────────────────────────────────────────────────────┐
│              Redis 分布式锁 (SETNX)                        │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  加锁:                                                   │
│  ┌─────────────────────────────────────────────────┐     │
│  │  # key   value(唯一标识)  过期时间              │     │
│  │  SET lock:order:1001 uuid NX EX 30             │     │
│  │                                                 │     │
│  │  # NX = Not Exist 才设置 (互斥)                 │     │
│  │  # EX = 秒级过期 (防死锁)                       │     │
│  │  # 值 = 客户端唯一 ID (防误删)                  │     │
│  └─────────────────────────────────────────────────┘     │
│                                                          │
│  解锁 (必须用 Lua 保证原子):                              │
│  ┌─────────────────────────────────────────────────┐     │
│  │  if redis.call("GET", KEYS[1]) == ARGV[1] then │     │
│  │      return redis.call("DEL", KEYS[1])         │     │
│  │  else                                          │     │
│  │      return 0                                  │     │
│  │  end                                           │     │
│  └─────────────────────────────────────────────────┘     │
│                                                          │
│  三个要素缺一不可:                                        │
│  ├── SET NX: 保证同一时刻只有一个客户端能设置成功          │
│  ├── EX 过期: 持有者崩溃后锁自动释放，防死锁              │
│  └── 唯一值: 防止删掉别人的锁                             │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 为什么不能 SETNX + EXPIRE 两条命令？

```java
// 错误写法：非原子，SETNX 成功后 EXPIRE 之前宕机 → 死锁
jedis.setnx(key, value);
jedis.expire(key, 30);

// 正确写法：SET 命令带 NX 和 EX，一条命令原子完成
jedis.set(key, value, SetParams.setParams().nx().ex(30));
```

### Redisson 加锁示例

```java
RLock lock = redissonClient.getLock("lock:order:" + orderId);
try {
    // waitTime: 获取锁等待时间; leaseTime: 持锁时间 (-1 用看门狗续期)
    boolean locked = lock.tryLock(2, 30, TimeUnit.SECONDS);
    if (!locked) {
        throw new RuntimeException("获取锁失败");
    }
    // 业务逻辑: 扣库存 / 创建订单
    doBusiness();
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

### 手写简易版 (面试手撕高频)

```java
public class RedisDistributedLock {

    private static final String UNLOCK_LUA =
        "if redis.call('get', KEYS[1]) == ARGV[1] then " +
        "  return redis.call('del', KEYS[1]) " +
        "else " +
        "  return 0 " +
        "end";

    private final StringRedisTemplate redis;
    private final String lockKey;
    private final String uniqueId;

    public RedisDistributedLock(StringRedisTemplate redis, String lockKey) {
        this.redis = redis;
        this.lockKey = lockKey;
        this.uniqueId = UUID.randomUUID().toString();
    }

    /** 加锁: NX + 过期，一条命令原子完成 */
    public boolean tryLock(long timeoutSeconds) {
        return Boolean.TRUE.equals(redis.opsForValue()
                .setIfAbsent(lockKey, uniqueId, Duration.ofSeconds(timeoutSeconds)));
    }

    /** 解锁: Lua 校验唯一值，防止误删 */
    public boolean unlock() {
        Long result = redis.execute(
            new DefaultRedisScript<>(UNLOCK_LUA, Long.class),
            List.of(lockKey), uniqueId);
        return result != null && result > 0;
    }
}
```

### 面试答法

> "Redis 分布式锁用 SET key value NX EX 实现互斥，value 放客户端唯一 ID，解锁时用 Lua 比对 value 后再 DEL，保证只有持有者能释放。关键是加锁、过期、唯一值三要素，以及加锁和设过期必须一条命令原子执行，避免 SETNX 成功但 EXPIRE 没执行导致死锁。"

## Q3: Redisson 看门狗机制？（高频）

### 为什么需要看门狗？

```
┌──────────────────────────────────────────────────────────┐
│              锁过期 vs 业务未完成                          │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  时间轴:                                                 │
│  ├─0s── 加锁成功 (TTL=30s)                               │
│  │                                                       │
│  ├─30s─ 锁自动过期释放                                   │
│  │      ▲ 但业务还没跑完!                                │
│  │      │                                                │
│  ├─31s─ 其他线程获取到同一把锁 → 并发问题!                │
│  │                                                       │
│  └─45s─ 原线程才执行 unlock → 把别人的锁删了 (更糟)      │
│                                                          │
│  矛盾:                                                   │
│  ├── TTL 太短: 业务没跑完锁就没了                         │
│  ├── TTL 太长: 持有者崩溃后长时间死锁                     │
│  └── 无法预知业务执行时长                                 │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 看门狗工作原理

```
┌──────────────────────────────────────────────────────────┐
│              Redisson Watchdog 机制                        │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  默认 leaseTime = -1 时启用看门狗                         │
│  ├── 初始 TTL: lockWatchdogTimeout (默认 30s)            │
│  ├── 后台线程: 每 10s (TTL/3) 检查一次                    │
│  │   ├── 若当前线程仍持有锁 → 续期到 30s                  │
│  │   └── 若已释放 / 不是持有者 → 停止续期                 │
│  └── 业务执行完 unlock 后，看门狗停止                     │
│                                                          │
│  时间轴:                                                 │
│  ├─0s── 加锁 TTL=30s                                     │
│  ├─10s─ 看门狗续期 → TTL=30s                             │
│  ├─20s─ 看门狗续期 → TTL=30s                             │
│  ├─25s─ 业务执行完 unlock → 锁删除，看门狗退出            │
│  └─ (若线程崩溃: 不续期, 30s 后锁自动过期)               │
│                                                          │
│  注意:                                                   │
│  ├── tryLock(waitTime, leaseTime>0) 显式指定 → 无看门狗   │
│  └── 集群模式看门狗同样有效 (续期发到对应节点)            │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 面试答法

> "看门狗解决的是锁过期时间与业务执行时长不匹配的问题。Redisson 默认 leaseTime 为 -1 时启动后台线程，每隔 10 秒（默认 TTL 的三分之一）检查当前线程是否还持有锁，是则续期到 30 秒；业务完成或线程崩溃则停止续期，锁在 TTL 内自动释放。这样既防止锁提前过期，又防止持有者崩溃后永久死锁。注意显式指定 leaseTime 时不会启用看门狗。"

## Q4: Redis 分布式锁的坑：过期时间、主从异步、锁误删？

### 三大坑

```
┌──────────────────────────────────────────────────────────┐
│              Redis 分布式锁常见坑                           │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  坑 1: 锁过期但业务未完成                                 │
│  ├── 业务执行 > TTL，锁被其他线程拿到                     │
│  └── 解决: 看门狗自动续期 / 业务幂等兜底                  │
│                                                          │
│  坑 2: 锁误删 (非持有者解锁)                              │
│  ┌─────────────────────────────────────────────────┐     │
│  │  线程 A 加锁 (value=A)，业务超时锁过期           │     │
│  │  线程 B 加锁 (value=B)                           │     │
│  │  线程 A 执行 DEL key → 把 B 的锁删了!            │     │
│  └─────────────────────────────────────────────────┘     │
│  └── 解决: unlock 用 Lua 校验 value == 自己的唯一 ID      │
│                                                          │
│  坑 3: 主从异步复制丢锁                                   │
│  ┌─────────────────────────────────────────────────┐     │
│  │  Client ──加锁──▶ Master (写入成功)             │     │
│  │                      │ 异步复制 (还没同步)      │     │
│  │                   Slave                         │     │
│  │  Master 宕机 → Slave 升主 → 锁丢失              │     │
│  │  另一个 Client 在新主上又加锁成功 → 两把锁!     │     │
│  └─────────────────────────────────────────────────┘     │
│  └── 解决: RedLock / 多数派写入 / 业务幂等 + 对账         │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 额外注意点

| 坑 | 表现 | 应对 |
|----|------|------|
| 时间跳跃/NTP 回拨 | 锁提前或延后过期 | 用 TTL 自然过期，避免依赖绝对时间 |
| 大 Key / 慢 Lua | 阻塞 Redis | 锁 key 保持短小，Lua 逻辑极简 |
| 重入未处理 | 同线程二次加锁死锁 | 用 Redisson 可重入锁 (hash 记录重入次数) |
| 阻塞等待过长 | 线程堆积 | tryLock 设置合理 waitTime，失败快速降级 |
| 非原子释放 | 误删别人的锁 | Lua 脚本 GET+DEL 原子执行 |

### 面试答法

> "主要有三个坑：一是业务没跑完锁就过期，要用看门狗续期；二是锁误删，解锁必须用 Lua 校验唯一值；三是主从异步复制导致锁丢失，极端情况下两个客户端同时持锁。所以 Redis 锁是 AP 模型，不能保证强一致。严格场景用 RedLock 或 ZooKeeper，同时业务侧做幂等和兜底。"

## Q5: RedLock 算法？争议？

### RedLock 基本思路

```
┌──────────────────────────────────────────────────────────┐
│              RedLock 算法 (多节点多数派)                    │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  前提: N 个独立 Redis 主节点 (如 5 个，非主从集群)         │
│                                                          │
│  加锁步骤:                                               │
│  1. 记录当前时间 T1                                      │
│  2. 依次向 N 个节点 SET key value NX EX TTL               │
│  3. 计算加锁耗时 = 当前时间 - T1                          │
│  4. 当且仅当:                                            │
│     ├── 在 ≥ N/2+1 (多数派) 个节点上加锁成功              │
│     └── 且总耗时 < TTL (锁未过期)                        │
│     才算加锁成功                                         │
│  5. 锁的有效时间 = TTL - 加锁耗时 - 时钟漂移              │
│  6. 解锁: 向所有节点发送解锁 (Lua 校验 value)             │
│                                                          │
│  示例 (5 节点):                                          │
│  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐               │
│  │ R1  │ │ R2  │ │ R3  │ │ R4  │ │ R5  │               │
│  │ 成功│ │ 成功│ │ 成功│ │ 失败│ │ 失败│               │
│  └─────┘ └─────┘ └─────┘ └─────┘ └─────┘               │
│    3 成功 ≥ 3 (多数派) → 加锁成功                        │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 争议与问题

| 争议点 | 说明 |
|--------|------|
| Martin Kleppmann 批评 | 时钟跳变、GC 停顿、网络延迟仍可能破坏互斥性 |
| 不是真正强一致 | 本质是「多数派写入」，不能证明绝对互斥 |
| 时钟依赖 | 节点间时钟漂移影响有效时间计算 |
| 性能下降 | 需要访问多个节点，延迟增加、可用性下降 |
| 实现复杂 | 故障处理、重试、锁续期都更复杂 |
| Redis 作者 antirez 回应 | 在假设时钟大致正确、无长时间进程暂停时可接受 |

```
┌──────────────────────────────────────────────────────────┐
│              Kleppmann 指出的时序问题                      │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  Client A                    Client B                    │
│    │                            │                        │
│    ├─ 获得多数派锁              │                        │
│    ├─ 业务执行中...             │                        │
│    ├─ GC 停顿 / 长时间阻塞      │                        │
│    │   (锁已过期但 A 还不知情)   │                        │
│    │                            ├─ 获得多数派锁           │
│    │                            ├─ 业务执行中...          │
│    ├─ 继续执行 (以为还持锁)     ├─ 业务执行中...          │
│    │                            │                        │
│    └── 两个 Client 同时进入临界区 → 互斥被破坏           │
│                                                          │
│  根因: 分布式系统无法完全依赖时钟与进程调度假设           │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 面试答法

> "RedLock 向 N 个独立 Redis 节点加锁，多数派成功且耗时小于 TTL 才算成功，目的是解决主从复制丢锁。但它有争议：Kleppmann 指出时钟跳变、GC 停顿仍可能破坏互斥，它并非严格线性一致。业界共识是：能接受极小概率互斥失败就用 Redis 锁 + 幂等兜底；强一致场景用 ZooKeeper/etcd 的 CP 方案。"

## Q6: ZooKeeper / etcd 分布式锁 vs Redis 锁对比？

| 维度 | Redis 锁 | ZooKeeper 锁 | etcd 锁 |
|------|----------|--------------|---------|
| 一致性 | AP（最终一致） | CP（ZAB 强一致） | CP（Raft 强一致） |
| 实现基础 | SET NX EX | 临时顺序节点 + Watch | Lease + Revision/Prefix |
| 性能 | 极高（内存、单点 RTT） | 中等（写要多数派） | 中等（Raft 提交） |
| 可靠性 | 主从异步可能丢锁 | 临时节点崩溃自动删除 | 租约到期自动释放 |
| 公平性 | 默认非公平（可队列实现） | 天然公平（顺序节点排队） | 可公平（排队） |
| 可重入 | Redisson 支持 | 需自行实现 | 需自行实现 |
| 运维成本 | 低（已有 Redis 即可用） | 高（ZK 集群维护） | 中（etcd 集群） |
| 适用场景 | 高并发、允许极小概率不一致 | 强一致、配置/选主 | 云原生、K8s 生态 |

### ZooKeeper 锁流程

```
┌──────────────────────────────────────────────────────────┐
│              ZooKeeper 分布式锁                           │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  /locks/order_1001/                                      │
│  ├── _c_0000000001  (Client A 创建的临时顺序节点)        │
│  ├── _c_0000000002  (Client B)                           │
│  └── _c_0000000003  (Client C)                           │
│                                                          │
│  规则:                                                   │
│  1. 每个客户端在目录下创建临时顺序节点                    │
│  2. 自己不是最小序号 → Watch 前一个节点                   │
│  3. 前一个节点删除 (释放/崩溃) → Watch 触发               │
│  4. 最小序号节点持有锁                                   │
│                                                          │
│  优势:                                                   │
│  ├── 羊群效应已优化: 只监听前驱，不全量 Watch             │
│  ├── 客户端崩溃 → 临时节点自动删除 → 不会死锁             │
│  └── 天然公平排队                                         │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 面试答法

> "Redis 锁性能最好，但主从复制是异步的，极端情况会丢锁，适合高并发、可接受极小概率不一致的场景。ZooKeeper 用临时顺序节点加 Watch，强一致、公平、崩溃自动释放，适合配置中心、选主、强一致扣减。etcd 用 Lease + Raft，K8s 生态常用。选型原则：性能优先选 Redis，正确性优先选 ZK/etcd。"

## Q7: 分布式锁的可重入、公平性、性能如何考虑？

### 三大特性设计

```
┌──────────────────────────────────────────────────────────┐
│              分布式锁进阶特性                              │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  可重入 (同线程可多次加锁):                               │
│  ┌─────────────────────────────────────────────────┐     │
│  │  Redis 结构:                                    │     │
│  │  HSET lock:order:1001                          │     │
│  │      threadId:owner-uuid  →  count=1           │     │
│  │                                                 │     │
│  │  二次 lock: count+1                             │     │
│  │  unlock:    count-1, count=0 时才 DEL          │     │
│  └─────────────────────────────────────────────────┘     │
│  └── Redisson RLock 默认可重入                           │
│                                                          │
│  公平性 (按申请顺序获得锁):                               │
│  ┌─────────────────────────────────────────────────┐     │
│  │  方案一: ZK 临时顺序节点 (天然公平)             │     │
│  │  方案二: Redis ZSet 队列                        │     │
│  │    ZADD lock_queue score=timestamp member=id   │     │
│  │    自己是最小 score → 持有锁                    │     │
│  │    否则 Watch 前一个 member                     │     │
│  │  方案三: Redisson RFairLock                     │     │
│  └─────────────────────────────────────────────────┘     │
│                                                          │
│  性能优化:                                               │
│  ├── 锁粒度细: 按业务 ID 加锁 (order:1001)，而非全局锁   │
│  ├── tryLock 快速失败: 避免线程堆积                     │
│  ├── 减少临界区: 只锁必要代码                            │
│  ├── 本地缓存 + 分段锁: 降低 Redis 往返                  │
│  └── Redisson 起用 Lua / Pipeline 减少 RTT               │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 选型对比

| 特性 | 需求不强时 | 需要时的方案 |
|------|------------|--------------|
| 可重入 | 可不做 | Redisson RLock / Hash 计数 |
| 公平性 | 可不做（吞吐优先） | ZK / Redisson FairLock |
| 高性能 | Redis 主从即可 | 细粒度 key + 快速失败 |
| 高可用 | 看门狗续期 | 多节点 / ZK 临时节点 |

### 面试答法

> "可重入用 Hash 记录持有线程和重入次数；公平性可以用 ZK 顺序节点或 Redis 队列排队，但会牺牲吞吐；性能上关键是锁粒度要细、临界区要短、获取锁失败要快速降级。绝大多数业务场景用 Redisson 非公平可重入锁就够了。"

## Q8: 数据库分布式锁方案？

### 实现方式

```
┌──────────────────────────────────────────────────────────┐
│              数据库分布式锁 (悲观 / 乐观)                   │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  方案一: 唯一索引 / 主键冲突 (悲观语义)                   │
│  ┌─────────────────────────────────────────────────┐     │
│  │  CREATE TABLE distributed_lock (               │     │
│  │      lock_name  VARCHAR(64) PRIMARY KEY,       │     │
│  │      owner      VARCHAR(64) NOT NULL,          │     │
│  │      expire_at  DATETIME NOT NULL              │     │
│  │  );                                            │     │
│  │                                                 │     │
│  │  加锁: INSERT INTO distributed_lock            │     │
│  │        VALUES ('order:1001', 'uuid', now()+30s)│     │
│  │        # 冲突 → 加锁失败                       │     │
│  │                                                 │     │
│  │  解锁: DELETE WHERE lock_name=? AND owner=?    │     │
│  └─────────────────────────────────────────────────┘     │
│                                                          │
│  方案二: SELECT ... FOR UPDATE (行锁)                    │
│  ┌─────────────────────────────────────────────────┐     │
│  │  BEGIN;                                        │     │
│  │  SELECT * FROM distributed_lock                │     │
│  │    WHERE lock_name='order:1001' FOR UPDATE;    │     │
│  │  -- 业务逻辑                                    │     │
│  │  -- 需要定时续期 / 超时释放                     │     │
│  │  COMMIT;                                       │     │
│  └─────────────────────────────────────────────────┘     │
│                                                          │
│  方案三: 乐观锁 (version 字段)                            │
│  └── UPDATE ... WHERE version=? 影响行数判断             │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 数据库锁 vs Redis / ZK

| 维度 | 数据库锁 | Redis 锁 | ZK 锁 |
|------|----------|----------|-------|
| 实现成本 | 低（已有 MySQL） | 中 | 高 |
| 性能 | 差（磁盘、行锁竞争） | 高 | 中 |
| 可靠性 | 依赖 DB 高可用 | 主从异步 | 强一致 |
| 死锁风险 | FOR UPDATE 有 | 超时自动释放 | 临时节点 |
| 适用场景 | 并发不高、不想引入组件 | 高并发通用 | 强一致 |
| 自动续期 | 需自行实现 | 看门狗 | Watch/Session |

```sql
-- 需要定时任务清理过期锁（防止持有者崩溃导致死锁）
DELETE FROM distributed_lock WHERE expire_at < NOW();
```

### 面试答法

> "数据库锁适合并发不高、不想引入 Redis/ZK 的场景。用唯一索引冲突实现互斥，或 FOR UPDATE 行锁，必须有过期时间字段和定时清理，否则持有者崩溃会死锁。性能上比 Redis 差很多，高并发场景不推荐。中小项目或内部工具可以用，核心交易链路还是 Redis/ZK。"

---

## 面试答法总结

> "分布式锁三要素：互斥、防死锁、持有者解锁。Redis 方案用 SET NX EX + Lua 解锁 + 看门狗续期，性能好但主从异步可能丢锁；RedLock 尝试多数派缓解但有争议；强一致用 ZooKeeper/etcd。落地时注意锁粒度、可重入、快速失败，关键业务还要有幂等和对账兜底——分布式锁是防线，不是绝对正确性的唯一保证。"

### 高频追问速查

| 追问 | 关键点 |
|------|--------|
| SETNX 有什么问题？ | 不能设过期 → 死锁；要 SET NX EX 原子 |
| 为什么解锁用 Lua？ | GET + DEL 非原子，防止误删他人锁 |
| 看门狗多久续期？ | 默认 TTL 30s，每 10s 续期一次 |
| 主从丢锁怎么办？ | 业务幂等 + 对账；或 RedLock / ZK |
| RedLock 为什么有争议？ | 时钟/停顿可破坏互斥，非严格强一致 |
| 高并发下如何优化？ | 细粒度 key、短临界区、tryLock 快速失败 |
