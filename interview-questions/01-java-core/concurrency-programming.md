### wait() 和 sleep() 的区别

| 维度 | wait() | sleep() |
|------|--------|---------|
| 所属类 | Object | Thread |
| 释放锁 | ✅ 释放 | ❌ 不释放 |
| 唤醒方式 | notify/notifyAll | 超时自动 |
| 使用前提 | 必须在同步块内 | 任意位置 |
| 本质 | 线程间通信 | 线程暂停 |

## Q2: synchronized 和 ReentrantLock 的区别？

| 维度 | synchronized | ReentrantLock |
|------|--------------|---------------|
| 实现层面 | JVM 层面 (monitorenter/monitorexit) | API 层面 (AQS) |
| 锁释放 | 自动释放 | 必须手动 unlock |
| 可中断 | 不支持 | lockInterruptibly |
| 公平锁 | 非公平 | 可选公平/非公平 |
| 条件变量 | 只有 wait/notify | 多个 Condition |
| 锁升级 | 偏向→轻量→重量级 | 不支持 |
| 性能 | JDK6后优化，差距小 | 灵活性更高 |

### 加分回答

> "synchronized 在 JDK 6 引入了**偏向锁 → 轻量级锁 → 重量级锁**的升级机制。偏向锁在对象头记录线程 ID，无竞争时不触发 CAS；轻量级锁通过 CAS 自旋竞争；自旋一定次数后升级为重量级锁，挂起等待线程。"

## Q3: synchronized 锁升级过程？

```
┌──────────────────────────────────────────────────────────┐
│              锁升级 (不可逆)                               │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  无锁 ──▶ 偏向锁 ──▶ 轻量级锁 ──▶ 重量级锁              │
│                                                          │
│  ┌─────────────────────────────────────────────────────┐ │
│  │  偏向锁 (Biased Locking)                            │ │
│  │  ├── 场景: 只有一个线程访问                          │ │
│  │  ├── 原理: 对象头 Mark Word 记录线程 ID              │ │
│  │  ├── 操作: 只需一次 CAS                             │ │
│  │  └── 撤销: 其他线程竞争时撤销, 有安全点停顿         │ │
│  ├─────────────────────────────────────────────────────┤ │
│  │  轻量级锁 (Lightweight Locking)                     │ │
│  │  ├── 场景: 两个线程交替执行 (无实际竞争)             │ │
│  │  ├── 原理: 在线程栈帧中创建 Lock Record             │ │
│  │  ├── 操作: CAS 将 Mark Word 复制到 Lock Record     │ │
│  │  └── 自旋: CAS 失败后自旋等待 (默认 10 次)          │ │
│  ├─────────────────────────────────────────────────────┤ │
│  │  重量级锁 (Heavyweight Locking)                     │ │
│  │  ├── 场景: 多线程实际竞争                           │ │
│  │  ├── 原理: 对象关联 Monitor (OS Mutex)              │ │
│  │  ├── 操作: 线程阻塞, 进入 EntryList                │ │
│  │  └── 开销: 用户态→内核态切换, 成本高               │ │
│  └─────────────────────────────────────────────────────┘ │
│                                                          │
│  对象头 Mark Word 结构 (64位):                           │
│  ┌───────┬──────┬──────┬──────┬──────┐                  │
│  │unused │hash  │ age  │biased│ lock │                  │
│  │ 25bit │ 31bit│ 4bit │ 1bit │ 2bit │                  │
│  └───────┴──────┴──────┴──────┴──────┘                  │
│                                                          │
│  JDK 15 废弃偏向锁 (JEP 374)                             │
│  原因: 启动开销大, 现代应用竞争多, 收益不明显            │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

## Q6: ReentrantLock 公平锁 vs 非公平锁？

```
┌──────────────────────────────────────────────────────────┐
│              公平锁 vs 非公平锁                            │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  非公平锁 (默认):                                        │
│  ┌──────────────────────────────────────────────┐        │
│  │  新线程来了 → 先尝试 CAS 抢锁                │        │
│  │  ├── 成功 → 直接执行                         │        │
│  │  └── 失败 → 进入 CLH 队列排队                │        │
│  │                                              │        │
│  │  优点: 减少线程切换, 吞吐量高                 │        │
│  │  缺点: 可能饿死排队线程                       │        │
│  └──────────────────────────────────────────────┘        │
│                                                          │
│  公平锁:                                                 │
│  ┌──────────────────────────────────────────────┐        │
│  │  新线程来了 → 检查队列中有没有等待线程        │        │
│  │  ├── 有 → 老老实实排队                        │        │
│  │  └── 没有 → 尝试获取锁                        │        │
│  │                                              │        │
│  │  hasQueuedPredecessors() 判断                 │        │
│  │  优点: 不会饿死                               │        │
│  │  缺点: 吞吐量低 (频繁切换)                    │        │
│  └──────────────────────────────────────────────┘        │
│                                                          │
│  源码关键 (tryAcquire):                                  │
│  if (!fair || !hasQueuedPredecessors()) {                │
│      if (compareAndSetState(0, acquires)) {              │
│          setExclusiveOwnerThread(current);               │
│          return true;                                    │
│      }                                                   │
│  }                                                       │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 四种拒绝策略

| 策略 | 行为 |
|------|------|
| AbortPolicy (默认) | 抛 RejectedExecutionException |
| CallerRunsPolicy | 调用者线程执行（降级） |
| DiscardPolicy | 静默丢弃 |
| DiscardOldestPolicy | 丢弃队列头部任务，重试提交 |

### 面试加分

> "阿里规范建议用自定义线程池，不用 Executors。因为 `newFixedThreadPool` 和 `newSingleThreadExecutor` 的队列是无界的 LinkedBlockingQueue，可能堆积大量任务导致 OOM；`newCachedThreadPool` 的最大线程数是 Integer.MAX_VALUE，可能创建大量线程。"

## Q8: execute 和 submit 的区别？

| 维度 | execute() | submit() |
|------|-----------|----------|
| 参数 | Runnable | Callable/Runnable |
| 返回值 | void | Future |
| 异常处理 | 直接抛出 (UncaughtHandler) | 包装在Future中 (get时抛出) |
| 源码差异 | 直接执行 | 包装为FutureTask |

```java
// submit 内部实现
public Future<?> submit(Runnable task) {
    RunnableFuture<Void> ftask = newFutureTask(task, null);
    execute(ftask);  // 最终还是调 execute
    return ftask;
}

// FutureTask.run() 内部
try {
    result = callable.call();
} catch (Throwable t) {
    setException(t);  // 异常被包装, 不会直接抛
}
```

## Q10: CountDownLatch vs CyclicBarrier vs Semaphore？

| 维度 | CountDownLatch | CyclicBarrier | Semaphore |
|------|----------------|---------------|-----------|
| 作用 | 等待N个任务完成 | N个线程同步 | 控制并发数 |
| 计数方式 | 递减到0 | 递增到N | 获取/释放 |
| 可重用 | ❌ 一次性 | ✅ 可重置 | ✅ |
| 触发点 | countDown()=0 | 所有线程到达 | acquire() |
| 典型场景 | 主线程等子任务 | 多线程同时开始 | 连接池/限流 |

### CountDownLatch 示例

```
┌─────────────────────────────────────────────┐
│  主线程                                      │
│  latch = new CountDownLatch(3)              │
│  │                                          │
│  ├──▶ 子线程1: 处理完 → latch.countDown()   │
│  ├──▶ 子线程2: 处理完 → latch.countDown()   │
│  ├──▶ 子线程3: 处理完 → latch.countDown()   │
│  │                                          │
│  latch.await()  // 阻塞等待计数归零         │
│  ▼                                          │
│  所有子任务完成, 继续执行                    │
└─────────────────────────────────────────────┘
```

### CyclicBarrier 示例

```
┌─────────────────────────────────────────────┐
│  barrier = new CyclicBarrier(3, () -> {     │
│      // 所有线程到达后执行 (汇总结果)        │
│  });                                        │
│                                             │
│  线程1: 处理 → barrier.await() // 阻塞      │
│  线程2: 处理 → barrier.await() // 阻塞      │
│  线程3: 处理 → barrier.await() // 阻塞      │
│  │                                          │
│  ▼ 全部到达, 同时放行                        │
└─────────────────────────────────────────────┘
```

## Q11: CompletableFuture 怎么用？

```
┌──────────────────────────────────────────────────────────┐
│              CompletableFuture 核心 API                    │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  创建:                                                   │
│  ├── CompletableFuture.supplyAsync(() -> queryDB())     │
│  ├── CompletableFuture.runAsync(() -> doSomething())    │
│  └── CompletableFuture.completedFuture(value)           │
│                                                          │

│  ┌──────────────────────────────────────────────────┐    │
│  │  supplyAsync(queryUser)                          │    │

│  │    .thenApply(order -> calculatePrice(order))    │    │

│  └──────────────────────────────────────────────────┘    │
│                                                          │
│  组合:                                                   │
│  ├── thenCombine: 两个都完成, 合并结果                   │
│  ├── thenCompose: 扁平化 (flatMap)                      │

│                                                          │
│  实战示例 (并行查询):                                    │
│  ┌──────────────────────────────────────────────────┐    │

│  │  var orderFuture = supplyAsync(() -> getOrders());│    │
│  │  var scoreFuture = supplyAsync(() -> getScore()); │    │
│  │                                                  │    │
│  │  CompletableFuture.allOf(userFuture, orderFuture,│    │
│  │                          scoreFuture).join();    │    │
│  │                                                  │    │
│  │  // 获取结果                                     │    │
│  │  User user = userFuture.join();                  │    │
│  │  List<Order> orders = orderFuture.join();        │    │
│  │  Score score = scoreFuture.join();               │    │
│  └──────────────────────────────────────────────────┘    │
│                                                          │
│  超时控制 (JDK 9+):                                      │
│  future.orTimeout(3, TimeUnit.SECONDS)                  │
│  future.completeOnTimeout(defaultValue, 3, SECONDS)     │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

## Q12: ForkJoinPool 和普通线程池的区别？

```
┌──────────────────────────────────────────────────────────┐
│          ForkJoinPool vs ThreadPoolExecutor              │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  ThreadPoolExecutor:                                     │
│  ┌─────────────────────────────────────┐                │
│  │  一个队列, 多个线程竞争              │                │
│  │  ┌───┐ ┌───┐ ┌───┐                 │                │
│  │  │ T1│ │ T2│ │ T3│  线程           │                │
│  │  └─┬─┘ └─┬─┘ └─┬─┘                 │                │
│  │    └─────┼─────┘                    │                │
│  │          ▼                          │                │
│  │  ┌───────────────────┐              │                │
│  │  │   共享队列         │              │                │
│  │  │ [t1][t2][t3]...   │              │                │
│  │  └───────────────────┘              │                │
│  └─────────────────────────────────────┘                │
│                                                          │
│  ForkJoinPool:                                           │
│  ┌─────────────────────────────────────┐                │
│  │  工作窃取 (Work-Stealing)           │                │
│  │  ┌─────┐  ┌─────┐  ┌─────┐         │                │
│  │  │ T1  │  │ T2  │  │ T3  │         │                │
│  │  │队列1│  │队列2│  │队列3│         │                │
│  │  │[t1] │  │[t2] │  │[t3] │         │                │
│  │  │[t4] │  │     │  │[t5] │         │                │
│  │  └──┬──┘  └──┬──┘  └──┬──┘         │                │
│  │     │        │   窃取   │            │                │
│  │     └────────┴─────────┘            │                │
│  │  每个线程有自己的双端队列            │                │
│  │  空闲线程从其他线程队尾偷任务        │                │
│  └─────────────────────────────────────┘                │
│                                                          │
│  适用场景:                                               │
```

## Q14: 死锁的条件和排查？

### 死锁四个必要条件

1. **互斥条件**: 资源不能共享
2. **占有并等待**: 持有资源的同时等待其他资源
3. **不可抢占**: 已获得的资源不能被强制夺走
4. **循环等待**: 存在等待环路

### 死锁示例

```java
// 线程A
synchronized(lockA) {
    // 持有 A, 等待 B
    synchronized(lockB) { ... }
}

// 线程B
synchronized(lockB) {
    // 持有 B, 等待 A
    synchronized(lockA) { ... }
}
```

### 排查方法

```
1. jps → 找到 Java 进程 PID
2. jstack <PID> → 打印线程堆栈
3. 搜索 "BLOCKED" + "waiting to lock"
4. 找到互相等待的两个线程
```

### 预防方法

- 固定加锁顺序 (都先锁 A 再锁 B)
- tryLock 超时放弃
- 使用并发工具代替锁 (ConcurrentHashMap)
- 死锁检测 (ThreadMXBean.findDeadlockedThreads())

## Q15: StampedLock 和读写锁的区别？

```
┌──────────────────────────────────────────────────────────┐
│        ReentrantReadWriteLock vs StampedLock              │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  ReentrantReadWriteLock 问题:                            │
│  ├── 读锁期间不能升级为写锁 (先读后写 → 死锁)           │
│  ├── 写线程可能饿死 (读多写少场景)                       │
│  └── 公平模式性能差                                      │
│                                                          │
│  StampedLock 三种模式:                                   │
│  ┌──────────────────────────────────────────────────┐    │
│  │  1. 写锁 (writeLock)                             │    │
│  │     long stamp = lock.writeLock();               │    │
│  │     try { ... } finally { lock.unlockWrite(stamp);}│   │
│  │                                                  │    │
│  │  2. 悲观读锁 (readLock)                          │    │
│  │     long stamp = lock.readLock();                │    │
│  │     try { ... } finally { lock.unlockRead(stamp);}│    │
│  │                                                  │    │
│  │  3. 乐观读 (tryOptimisticRead) ⭐ 核心优势       │    │
│  │     long stamp = lock.tryOptimisticRead();       │    │
│  │     // 不加锁, 只记录版本号                       │    │
│  │     // 读完后验证:                               │    │
│  │     if (lock.validate(stamp)) {                  │    │
│  │         // 期间没有写操作, 读成功                 │    │
│  │     } else {                                     │    │
│  │         // 期间有写操作, 升级为悲观读锁           │    │
│  │         stamp = lock.readLock();                 │    │
│  │     }                                            │    │
│  └──────────────────────────────────────────────────┘    │
│                                                          │
│  适用场景: 读多写少, 读操作时间短                         │
│  注意: 不可重入, 不支持 Condition                        │
│                                                          │
└──────────────────────────────────────────────────────────┘
```
