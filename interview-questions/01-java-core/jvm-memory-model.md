# JVM & 内存模型

## Q1: JVM 内存区域划分？各自作用？

```
┌─────────────────────────────────────────────────────────┐
│                    JVM 内存结构                          │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  线程私有                          线程共享              │
│  ┌──────────────┐                ┌──────────────┐       │
│  │  程序计数器    │                │     堆       │       │
│  │  (PC)        │                │  (Heap)      │       │
│  ├──────────────┤                │              │       │
│  │  虚拟机栈      │                │  ┌────────┐  │       │
│  │  (Stack)     │                │  │ 新生代  │  │       │
│  │  ├─栈帧       │                │  │Eden│S0│S1│  │       │
│  │  │ ├─局部变量  │                │  └────────┘  │       │
│  │  │ ├─操作数栈  │                │  ┌────────┐  │       │
│  │  │ ├─动态链接  │                │  │  老年代  │  │       │
│  │  │ └─返回地址  │                │  └────────┘  │       │
│  │  └─...       │                ├──────────────┤       │
│  ├──────────────┤                │  方法区/元空间 │       │
│  │  本地方法栈    │                │  (Metaspace) │       │
│  │  (Native)    │                └──────────────┘       │
│  └──────────────┘                                        │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 回答要点

- **程序计数器**：当前线程执行字节码的行号指示器，唯一不会 OOM 的区域
- **虚拟机栈**：每个方法调用创建一个栈帧，存局部变量表、操作数栈、动态链接、方法出口
- **本地方法栈**：Native 方法服务（如 `Thread.start0()`）
- **堆**：对象实例 & 数组，GC 主战场，分新生代（Eden + S0 + S1）和老年代
- **方法区/元空间**：类信息、常量池、静态变量。JDK 8 后元空间取代永久代，使用本地内存

## Q2: 常见 GC 算法和收集器？

### GC 算法对比

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 标记-清除 | 标记→清除 | 简单 | 内存碎片 |
| 标记-整理 | 标记→移动 | 无碎片 | 移动开销大 |
| 复制 | Eden→S区 | 无碎片 | 空间浪费 (50%) |
| 分代 | 新生+老年代 | 针对性强 | 现代GC已弱化分代 |

### 收集器对比

| 收集器 | 作用区域 | 算法 | 特点 |
|--------|----------|------|------|
| Serial | 新生代 | 复制 | 单线程，Client模式 |
| ParNew | 新生代 | 复制 | 多线程版Serial |
| Parallel | 新生代 | 复制 | 吞吐量优先 |
| CMS | 老年代 | 标记-清除 | 低延迟，已废弃 |
| G1 | 整堆 | 分区 | JDK9默认，可控停顿 |
| ZGC | 整堆 | 染色指针 | 亚毫秒停顿，JDK15+ |

### 面试答法

> "JDK 8 默认 Parallel Scavenge + Old，JDK 9+ 默认 G1。G1 将堆划分为多个 Region，通过 Remembered Set 追踪跨代引用，可以设定目标停顿时间（-XX:MaxGCPauseMillis）。如果对延迟要求极高，可以考虑 ZGC，停顿时间在亚毫秒级别。"

## Q3: 类加载机制？什么是双亲委派？如何打破？

```
┌─────────────────────────────────────────────────────┐
│              双亲委派模型                             │
├─────────────────────────────────────────────────────┤
│                                                     │
│   Bootstrap ClassLoader   ←  加载 rt.jar 等核心类   │
│          ▲                                          │
│          │  委派                                      │
│   Extension ClassLoader   ←  加载 ext 目录          │
│          ▲                                          │
│          │  委派                                      │
│   Application ClassLoader ←  加载 classpath         │
│          ▲                                          │
│          │  委派                                      │
│   Custom ClassLoader      ←  自定义加载             │
│                                                     │
│   流程: loadClass() → findLoadedClass()             │
│        → parent.loadClass() → findClass()           │
│                                                     │
└─────────────────────────────────────────────────────┘
```

### 打破双亲委派的场景

- **SPI 机制**：`DriverManager` 由 Bootstrap 加载，但实现类在 classpath → 使用 `Thread.currentThread().getContextClassLoader()`
- **Tomcat**：每个 WebApp 有自己的 ClassLoader，优先加载应用自身的类
- **OSGi**：网状委托模型
- **热部署**：自定义 ClassLoader 重新加载修改后的类

## Q4: 如何排查 OOM 问题？

### 回答模板

> "分三步：**发现问题 → 定位原因 → 解决问题**。"

```
1. 发现: 监控告警 (Prometheus/Grafana) 或日志报 OOM
2. 定位:
   - 启动时加 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/dump.hprof
   - 用 MAT / JVisualVM 分析 dump 文件
   - 查看 Dominator Tree 找到占用内存最大的对象
   - 结合代码找到泄漏点 (如集合只加不删、未关闭的连接、缓存无上限)
3. 解决: 修复代码 + 调整 JVM 参数
```

### 常见 OOM 场景

| 场景 | 原因 | 解决方案 |
|------|------|----------|
| Java heap space | 堆内存不足 | 增大堆内存 / 排查内存泄漏 |
| Metaspace | 类加载过多 | 检查动态代理/反射 |
| GC overhead limit exceeded | GC 耗时过长 | 排查内存泄漏 |
| unable to create new native thread | 线程数过多 | 减少线程 / 调整系统限制 |

## Q5: 对象创建过程？内存如何分配？（高频）

```
┌──────────────────────────────────────────────────────────┐
│                  对象创建过程                              │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  new Foo() 触发:                                         │
│                                                          │
│  1. 类加载检查                                           │
│     └── 常量池是否有该类符号引用，没有则先加载类          │
│                                                          │
│  2. 分配内存                                             │
│     ├── 指针碰撞 (Bump the Pointer)                      │
│     │   └── 堆规整时使用 (如 Serial/ParNew + 标记-整理)  │
│     ├── 空闲列表 (Free List)                             │
│     │   └── 堆不规整时使用 (如 CMS + 标记-清除)          │
│     └── 并发安全: CAS + 失败重试 / TLAB                  │
│                                                          │
│  3. 初始化零值                                           │
│     └── int=0, boolean=false, 引用=null (不执行构造)     │
│                                                          │
│  4. 设置对象头                                           │
│     ├── Mark Word: hashcode、GC分代年龄、锁状态          │
│     └── 类型指针: 指向方法区的类元数据                   │
│                                                          │
│  5. 执行 <init> 构造方法                                 │
│     └── 按代码初始化字段，执行实例初始化块               │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 内存分配策略

| 策略 | 说明 |
|------|------|
| 对象优先在 Eden 分配 | 大多数对象朝生夕灭，Minor GC 频繁但快 |
| 大对象直接进老年代 | `-XX:PretenureSizeThreshold`，避免大对象在新生代复制 |
| 长期存活对象进老年代 | 年龄计数器，默认 15 次 GC 后晋升 (`-XX:MaxTenuringThreshold`) |
| 动态年龄判定 | Survivor 中相同年龄对象总大小 > Survivor 一半，≥该年龄的直接晋升 |
| 空间分配担保 | Minor GC 前检查老年代剩余空间是否 > 新生代总对象，失败则 Full GC |

### 面试答法

> "对象创建分五步：**类加载检查 → 分配内存 → 初始化零值 → 设置对象头 → 执行构造**。内存分配根据堆是否规整选指针碰撞或空闲列表，多线程用 TLAB 或 CAS 保证安全。多数对象在 Eden 分配，大对象直接进老年代，熬过多次 GC 的对象晋升老年代。"

## Q6: 如何判断对象是否存活？引用类型？（高频）

### 两种存活判定

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 引用计数 | 每次引用 +1，失效 -1 | 简单 | 循环引用无法回收 |
| 可达性分析 | GC Roots 不可达即死亡 | 主流 HotSpot 采用 | 需要 STW 时确定 GC Roots |

### GC Roots 包括

- 虚拟机栈中引用的对象（局部变量）
- 方法区中静态属性、常量引用的对象
- 本地方法栈中 JNI 引用的对象
- synchronized 锁持有的对象

### 四种引用类型

| 类型 | 回收时机 | 用途 | 示例 |
|------|----------|------|------|
| 强引用 | 从不回收 | 普通对象 | `Object obj = new Object()` |
| 软引用 | 内存不足时回收 | 缓存 | `SoftReference<byte[]>` |
| 弱引用 | 下次 GC 必回收 | ThreadLocalMap | `WeakReference` |
| 虚引用 | 随时回收 | 跟踪回收、直接内存释放 | `PhantomReference` |

```java
// 软引用做缓存示例
SoftReference<Map<String, Object>> cache =
        new SoftReference<>(new HashMap<>());
// 内存充足时 map 可能还在，内存紧张时会被回收

// 弱引用：ThreadLocal 内部 Entry 继承 WeakReference
// 防止线程池场景下 ThreadLocal 泄漏
```

### 面试答法

> "HotSpot 用**可达性分析**判断存活，从 GC Roots 出发，不可达的对象在 finalize() 后回收。引用分强、软、弱、虚四种，软引用适合做缓存，弱引用常用于 ThreadLocal 防泄漏，虚引用配合引用队列跟踪对象回收时机。"

## Q7: 常用 JVM 参数有哪些？生产环境怎么配？

### 核心参数速查

| 参数 | 作用 | 生产建议 |
|------|------|----------|
| `-Xms` / `-Xmx` | 堆初始/最大 | 设为相等，避免动态扩缩 |
| `-Xmn` | 新生代大小 | 约堆的 1/3 ~ 1/2 |
| `-Xss` | 线程栈大小 | 默认 1M，够用即可 |
| `-XX:MetaspaceSize` | 元空间初始 | 按类数量预估 |
| `-XX:MaxMetaspaceSize` | 元空间上限 | 建议设置上限 |
| `-XX:+UseG1GC` | 使用 G1 | JDK9+ 默认 |
| `-XX:MaxGCPauseMillis` | G1 目标停顿 | 200ms 左右 |
| `-XX:+HeapDumpOnOutOfMemoryError` | OOM 时 dump | 生产必开 |
| `-XX:HeapDumpPath` | dump 路径 | 指到大容量目录 |
| `-XX:+PrintGCDetails` | GC 日志 | JDK9+: `-Xlog:gc*` |

### 生产配置示例（8C16G）

```bash
java -jar app.jar \
  -Xms8g -Xmx8g \
  -Xmn4g \
  -XX:MetaspaceSize=256m \
  -XX:MaxMetaspaceSize=512m \
  -XX:+UseG1GC \
  -XX:MaxGCPauseMillis=200 \
  -XX:InitiatingHeapOccupancyPercent=45 \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/data/logs/heap.hprof \
  -Xlog:gc*:file=/data/logs/gc.log:time,uptime,level,tags:filecount=10,filesize=50m
```

### 面试关键点

- **Xms = Xmx**：避免堆反复扩容带来的性能抖动
- **不要盲目调大堆**：Full GC 时间变长，可能造成更久卡顿
- **必须开启 HeapDump**：OOM 后没有 dump 几乎无法事后分析
- **容器环境**：注意 `-XX:MaxRAMPercentage`，并限制与 cgroup 内存一致

### 面试答法

> "生产上至少配好堆大小（Xms=Xmx）、GC 收集器与停顿目标、Metaspace 上限、OOM dump、GC 日志。8G 堆 + G1 + 目标停顿 200ms 是常见起点，具体要压测后根据 GC 日志微调，而不是拍脑袋调参。"

## Q8: 类加载过程详细步骤？初始化时机？

```
┌──────────────────────────────────────────────────────────┐
│                   类加载全过程                            │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载        │
│                                                          │
│  加载 (Loading):                                         │
│  ├── 通过全限定名获取二进制字节流                        │
│  ├── 转为方法区的运行时数据结构                          │
│  └── 生成对应的 Class 对象                               │
│                                                          │
│  验证 (Verification):                                    │
│  ├── 文件格式、元数据、字节码、符号引用验证              │
│  └── 保证字节码不会危害虚拟机                            │
│                                                          │
│  准备 (Preparation):                                     │
│  ├── 静态变量赋「零值」                                  │
│  └── final static 在此赋「ConstantValue」                │
│                                                          │
│  解析 (Resolution):                                      │
│  └── 符号引用 → 直接引用（类、字段、方法）               │
│                                                          │
│  初始化 (Initialization):                                │
│  └── 执行 <clinit>：静态变量赋值 + 静态代码块            │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 初始化时机（主动引用）

- `new` 对象、读写静态字段（非 final）、调用静态方法
- 反射调用 `Class.forName()` / `newInstance()`
- 初始化子类时父类尚未初始化
- 含 `main()` 的主类
- JDK7 动态语言支持的 MethodHandle 解析结果为 REF_getStatic 等

**被动引用不初始化**：通过子类引用父类静态字段、数组定义、引用常量（编译期已入常量池）。

### `<clinit>` 特点

- 编译器收集静态变量赋值与 static 块合并生成，顺序与源码一致
- 虚拟机会加锁保证 `<clinit>` 只执行一次（线程安全）
- 父类的 `<clinit>` 先于子类执行

### 面试答法

> "类加载分**加载、验证、准备、解析、初始化**。准备阶段给静态变量赋零值，初始化才执行 `<clinit>` 真正赋值。只有主动引用才触发初始化，比如 new、调静态方法、反射；像子类访问父类静态字段、访问编译期常量都是被动引用，不会初始化子类。"
