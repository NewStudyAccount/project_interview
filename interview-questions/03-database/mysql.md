# MySQL

## Q1: 索引为什么用 B+ 树而不是 B 树/Hash？

```
┌──────────────────────────────────────────────────────────┐
│              B+ 树 vs B 树 vs Hash                        │
├──────────────┬───────────┬───────────┬───────────────────┤
│     维度      │   B+ 树   │   B 树    │     Hash          │
├──────────────┼───────────┼───────────┼───────────────────┤
│  查询效率     │  O(logN)  │  O(logN)  │  O(1)             │
│  范围查询     │  ✅ 链表  │  ❌ 中序  │  ❌ 不支持        │
│  排序         │  ✅ 天然  │  ❌ 需要  │  ❌ 不支持        │
│  磁盘IO      │  更少     │  较多     │  取决于冲突        │
│  树高         │  更矮     │  更高     │  -                │
│  适合场景     │  磁盘索引 │  内存索引 │  等值查询          │
└──────────────┴───────────┴───────────┴───────────────────┘

B+ 树优势:
├── 非叶子节点只存 key，单节点能存更多 key → 树更矮 → IO 更少
├── 叶子节点用链表连接 → 天然支持范围查询
├── 查询路径长度一致 → 性能稳定
└── 所有数据都在叶子节点 → 查询效率一致
```

## Q2: 聚簇索引 vs 非聚簇索引？

| 维度 | 聚簇索引 | 非聚簇索引 (二级索引) |
|------|----------|----------------------|
| 存储方式 | 数据和索引在一起 | 索引和数据分开 |
| 叶子节点 | 存完整数据行 | 存主键值 |
| 数量 | 一个 (主键索引) | 多个 |
| 查询 | 直接获取数据 | 需要回表 (除非覆盖索引) |
| 代表 | InnoDB 主键索引 | 普通索引、唯一索引 |

### 回表与覆盖索引

```
┌──────────────────────────────────────────────────────────┐
│                    回表查询                               │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  SELECT * FROM user WHERE name = '张三'                  │
│                                                          │
│  1. 在 name 索引树上查找 → 找到主键 id = 100            │
│  2. 在主键索引树上查找 → 获取完整数据行                  │
│                                                          │
│  ┌─────────────┐         ┌─────────────┐                │
│  │  name 索引   │         │  主键索引    │                │
│  │  name=张三   │──回表──▶│  id=100     │                │
│  │  id=100     │         │  完整数据    │                │
│  └─────────────┘         └─────────────┘                │
│                                                          │
└──────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────┐
│                    覆盖索引                               │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  SELECT id, name FROM user WHERE name = '张三'           │
│                                                          │
│  在 name 索引树上就能获取所有需要的字段 → 无需回表        │
│                                                          │
│  EXPLAIN 中 Extra 显示: Using index                      │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

## Q3: 索引失效的场景？

```
┌──────────────────────────────────────────────────────────┐
│                  索引失效场景                              │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  1. 违反最左前缀原则                                     │
│     联合索引 (a, b, c):                                  │
│     ├── WHERE a=1 AND b=2 AND c=3  ✅ 全部命中          │
│     ├── WHERE a=1 AND b=2          ✅ 命中 a, b         │
│     ├── WHERE a=1                  ✅ 命中 a             │
│     ├── WHERE b=2 AND c=3          ❌ 跳过 a            │
│     └── WHERE c=3                  ❌ 跳过 a, b         │
│                                                          │
│  2. 在索引列上做运算或函数                                │
│     ├── WHERE age + 1 = 18       ❌                     │
│     ├── WHERE YEAR(create_time) = 2024  ❌              │
│     └── 解决: WHERE age = 17 / WHERE create_time        │
│              BETWEEN '2024-01-01' AND '2024-12-31'       │
│                                                          │
│  3. 隐式类型转换                                         │
│     phone 是 varchar:                                    │
│     ├── WHERE phone = 13800138000  ❌ 字符串→数字       │
│     └── WHERE phone = '13800138000'  ✅                 │
│                                                          │
│  4. LIKE 以 % 开头                                       │
│     ├── WHERE name LIKE '张%'    ✅                     │
│     ├── WHERE name LIKE '%张'    ❌                     │
│     └── WHERE name LIKE '%张%'   ❌                     │
│                                                          │
│  5. OR 条件中有非索引列                                  │
│     ├── WHERE indexed_col = 1 OR non_indexed = 2  ❌    │
│     └── 解决: 给 non_indexed 也加索引                   │
│                                                          │
│  6. 使用 != 或 <>                                        │
│     ├── WHERE status != 1        ❌ (可能全表扫描)      │
│     └── 取决于数据分布，优化器判断                       │
│                                                          │
│  7. IS NULL / IS NOT NULL                                │
│     ├── 取决于 NULL 值的比例                             │
│     └── NULL 值过多时可能失效                            │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

## Q4: EXPLAIN 执行计划怎么看？

```sql
EXPLAIN SELECT * FROM user WHERE name = '张三';
```

| 字段 | 说明 | 关注点 |
|------|------|--------|
| id | 查询序号 | 相同从上到下，不同从大到小 |
| select_type | 查询类型 | SIMPLE/PRIMARY/SUBQUERY |
| table | 表名 | - |
| type | 访问类型 | 重点! system > const > eq_ref > ref > range > index > ALL |
| possible_keys | 可能用到的索引 | - |
| key | 实际用到的索引 | NULL 表示没用索引 |
| key_len | 索引长度 | 越短越好 |
| rows | 扫描行数 | 越少越好 |
| Extra | 额外信息 | 重点! |

### type 访问类型详解

| type | 说明 | 示例 |
|------|------|------|
| system | 表只有一行 | 系统表 |
| const | 主键/唯一索引等值查询 | WHERE id = 1 |
| eq_ref | 关联查询使用主键/唯一索引 | JOIN ON ... |
| ref | 非唯一索引等值查询 | WHERE name = '张三' |
| range | 索引范围查询 | WHERE age > 18 |
| index | 全索引扫描 | SELECT 索引列 |
| ALL | 全表扫描 | 需要优化! |

### Extra 常见值

| Extra | 说明 |
|-------|------|
| Using index | 覆盖索引，好事 |
| Using where | Server 层过滤 |
| Using temporary | 使用临时表，需优化 |
| Using filesort | 文件排序，需优化 |
| Using index condition | 索引下推 (ICP) |

```
┌──────────────────────────────────────────────────────────┐
│                 四种隔离级别                               │

```

### MVCC 多版本并发控制

```
┌──────────────────────────────────────────────────────────┐
│              MVCC 核心机制                                │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  每行记录隐含 3 个字段:                                   │
│  ├── DB_TRX_ID    最近修改的事务 ID                      │
│  ├── DB_ROLL_PTR  回滚指针 (指向 undo log)               │
│  └── DB_ROW_ID    隐藏主键                               │
│                                                          │
│  ReadView (快照):                                        │
│  ├── m_ids        创建时活跃的事务 ID 列表               │
│  ├── min_trx_id   活跃事务最小 ID                        │
│  ├── max_trx_id   下一个分配的事务 ID                    │
│  └── creator_trx_id  创建者事务 ID                       │
│                                                          │
│  可见性判断:                                              │
│  ├── trx_id < min_trx_id       → 可见 (已提交)          │
│  ├── trx_id ≥ max_trx_id       → 不可见 (将来事务)      │
│  ├── trx_id 在 m_ids 中        → 不可见 (未提交)        │
│  └── trx_id 不在 m_ids 中      → 可见 (已提交)          │
│                                                          │
│  RC vs RR 的区别:                                        │
│  ├── RC: 每次 SELECT 生成新的 ReadView                   │
│  └── RR: 事务中第一次 SELECT 生成，后续复用              │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

## Q6: InnoDB 的锁机制？

```
┌──────────────────────────────────────────────────────────┐
│                  InnoDB 锁类型                            │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  按粒度:                                                 │
│  ├── 表锁: lock tables ... read/write                   │
│  ├── 意向锁: IX/IS (表级，标识事务意图)                  │
│  └── 行锁: 记录锁/间隙锁/临键锁                         │
│                                                          │
│  行锁详解:                                               │
│  ├── Record Lock  (记录锁): 锁定索引记录                 │
│  ├── Gap Lock     (间隙锁): 锁定索引之间的间隙           │
│  ├── Next-Key Lock (临键锁): 记录锁 + 间隙锁             │
│  └── Insert Intention Lock (插入意向锁)                  │
│                                                          │
│  唯一索引等值查询:                                       │
│  ├── 记录存在 → Record Lock                             │
│  └── 记录不存在 → Gap Lock                              │
│                                                          │
│  非唯一索引等值查询:                                     │
│  ├── 记录存在 → Next-Key Lock + Gap Lock (右侧)         │
│  └── 记录不存在 → Gap Lock                              │
│                                                          │
│  RR 级别下 Next-Key Lock 解决幻读:                       │
│  锁住记录 + 间隙，阻止其他事务插入                       │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 分页优化

```sql
-- ❌ 慢: 深分页
SELECT * FROM user ORDER BY id LIMIT 1000000, 10;

-- ✅ 快: 延迟关联
SELECT * FROM user u
INNER JOIN (
    SELECT id FROM user ORDER BY id LIMIT 1000000, 10
) AS tmp ON u.id = tmp.id;

-- ✅ 快: 游标分页 (需要上一页最后一条的 id)
SELECT * FROM user WHERE id > 1000000 ORDER BY id LIMIT 10;
```

## Q9: 分库分表后如何分页/排序/join？全局 ID？

### 跨库查询难题

```
┌──────────────────────────────────────────────────────────┐
│              分库分表后的查询问题                          │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  分页 (LIMIT offset, size):                              │
│  ├── 各分片执行 limit offset*size, size                  │
│  ├── 中间件归并后取前 size 条                            │
│  └── 深分页 offset 很大时各库都要扫大量数据              │
│                                                          │
│  排序 (ORDER BY):                                        │
│  ├── 各分片本地排序                                      │
│  └── 归并排序 (类似多路归并)                             │
│                                                          │
│  JOIN:                                                   │
│  ├── 跨库 JOIN 不支持 → 应用层组装                      │
│  ├── 字段冗余 (订单表冗余商品名)                         │
│  ├── 全局表 / 广播表 (字典表同步到各库)                  │
│  └── 绑定表 (分片键一致的表可本地 JOIN)                  │
│                                                          │
│  聚合 (COUNT/SUM/AVG):                                   │
│  ├── 各分片本地聚合                                      │
│  └── 中间件二次聚合                                      │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 全局唯一 ID 方案

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| UUID | 32 位字符串 | 简单、无中心 | 无序、索引分裂、太长 |
| 数据库自增 | 不同库步长错开 | 简单可控 | 扩容麻烦、性能瓶颈 |
| Redis INCR | 原子自增 | 高性能、趋势递增 | 依赖 Redis 可用性 |
| 雪花算法 | 时间戳+机器ID+序列号 | 本地生成、趋势递增 | 时钟回拨问题 |
| Leaf / 号段 | 批量取号到内存 | 高可用、低延迟 | 实现较复杂 |

```java
// 雪花算法 ID 结构 (64 bit)
// 0 | 41 bit 时间戳 | 10 bit 机器 | 12 bit 序列
long id = (timestamp << 22) | (workerId << 12) | sequence;
```

### 面试答法

> "分库分表后跨分片查询靠**各库查、中间件归并**：分页是各片取数再归并取前 N，排序是多路归并，JOIN 靠冗余/绑定表/应用层组装。全局 ID 优先雪花或 Leaf 号段，避免 UUID 导致索引无序。深分页用游标或延迟关联优化。"

## Q10: MySQL 主从复制原理？延迟问题？

```
┌──────────────────────────────────────────────────────────┐
│                主从复制原理                                │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  Master                          Slave                   │
│  ┌────────┐   ①binlog   ┌────────────────────┐          │
│  │ 事务   │────────────▶│ I/O Thread          │          │
│  │ 提交   │             │ 拉取 binlog →       │          │
│  │ 写     │             │ 中继日志 relay log  │          │
│  │ binlog │             └─────────┬──────────┘          │
│  └────────┘                       │ ②回放               │
│                                   ▼                     │
│                         ┌────────────────────┐          │
│                         │ SQL Thread          │          │
│                         │ 重放 relay log      │          │
│                         │ 更新从库数据        │          │
│                         └────────────────────┘          │
│                                                          │
│  三个线程: Master Dump / Slave I/O / Slave SQL           │
│                                                          │
│  binlog 格式:                                            │
│  ├── STATEMENT: 记录 SQL（可能主从不一致）               │
│  ├── ROW: 记录行变更（推荐，数据一致）                   │
│  └── MIXED: 混合模式                                     │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 复制延迟原因与优化

| 原因 | 优化 |
|------|------|
| 从库单线程回放（旧版本） | 开启并行复制 `slave_parallel_workers` |
| 大事务 | 拆分事务，避免单事务更新过多行 |
| 从库硬件差 | 从库配置不低于主库 |
| 网络抖动 | 同机房部署、监控 Seconds_Behind_Master |
| 从库读压力大 | 多从库分流、缓存挡读 |

### 延迟带来的问题

- **读写分离读到旧数据**：注册后立刻登录失败
- **解决方案**：
  - 关键读走主库
  - 写后读用缓存标记/强制主库
  - 半同步复制 `rpl_semi_sync`（至少一个从库收到 binlog 才返回）
  - 业务容忍最终一致

### 面试答法

> "主从复制三线程：主库 Dump 发 binlog，从库 I/O 写 relay log，SQL 线程回放。延迟主要来自单线程回放和大事务，用并行复制、拆事务、半同步缓解。业务上关键读走主库，或写后读粘滞主库，接受最终一致。"

## Q11: MySQL 深分页为什么慢？如何优化？

### 慢的原因

```
┌──────────────────────────────────────────────────────────┐
│            SELECT * FROM user ORDER BY id                 │
│                 LIMIT 1000000, 10                         │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  实际执行:                                               │
│  1. 在索引/主键上定位到第 1000000 条                    │
│  2. 扫描并丢弃前 1000000 行（全取回内存再丢弃）          │
│  3. 只返回 10 行                                         │
│                                                          │
│  offset 越大 → 丢弃越多 → 越慢                          │
│  复杂度 ≈ O(offset + size)                               │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 优化方案对比

| 方案 | SQL 思路 | 适用场景 |
|------|----------|----------|
| 游标分页 | `WHERE id > #{lastId} LIMIT 10` | 顺序翻页、瀑布流 |
| 延迟关联 | 子查询只查 id，再回表 | 跳页、需要 offset |
| 业务折衷 | 禁止跳到极大页码 | 不要求任意跳页 |
| 冗余汇总表 | 预计算分页辅助 | 报表类 |

```sql
-- ❌ 慢: 深分页
SELECT * FROM user ORDER BY id LIMIT 1000000, 10;

-- ✅ 延迟关联: 子查询走覆盖索引，只回表 10 行
SELECT u.* FROM user u
INNER JOIN (
    SELECT id FROM user ORDER BY id LIMIT 1000000, 10
) AS tmp ON u.id = tmp.id;

-- ✅ 游标分页: 记住上一页最后一条 id
SELECT * FROM user WHERE id > 1000000 ORDER BY id LIMIT 10;
```

### 面试关键点

- `LIMIT offset, n` 的 offset 会被扫描并丢弃，不是直接跳过
- 延迟关联把「扫描丢弃」压缩到只扫索引列，避免大量回表
- 游标分页无法跳页，但性能稳定 O(size)
- 深分页 + 排序字段无索引时更糟，可能 filesort + 临时表

### 面试答法

> "深分页慢是因为 offset 越大，引擎要扫描并丢弃越多行。优化有三招：**游标分页**（`id > lastId`，适合顺序翻）、**延迟关联**（子查询只取 id 再回表）、**限制跳页**。生产上列表页优先游标，导出报表用延迟关联或离线任务。"
