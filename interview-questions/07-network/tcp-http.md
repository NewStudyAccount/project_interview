# 计算机网络 (TCP/HTTP)

## Q1: TCP 三次握手/四次挥手？为什么不是两次？（高频）

### 三次握手

```
┌──────────────────────────────────────────────────────────┐
│              TCP 三次握手 (Three-way Handshake)            │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  Client                         Server                   │
│    │                               │                     │
│    │  ① SYN, seq=x                 │                     │
│    │ ─────────────────────────────▶│  SYN_SENT           │
│    │                               │                     │
│    │  ② SYN+ACK, seq=y, ack=x+1    │                     │
│    │ ◀─────────────────────────────│  SYN_RCVD           │
│    │                               │                     │
│    │  ③ ACK, seq=x+1, ack=y+1      │                     │
│    │ ─────────────────────────────▶│  ESTABLISHED        │
│    │  ESTABLISHED                  │                     │
│                                                          │
│  为什么是三次:                                            │
│  ├── 双方确认: 自己的发送/接收能力 + 对方的发送/接收能力    │
│  ├── 同步初始序列号 (ISN)，双方各自确认对方的 ISN          │
│  └── 防止历史重复连接请求造成资源浪费                       │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 为什么不是两次？

| 原因 | 说明 |
|------|------|
| 防止历史连接 | 旧的 SYN 报文延迟到达，两次握手就会建立无效连接 |
| 双方确认能力 | 两次只能确认客户端能收发，无法确认服务端能收发 |
| 同步序列号 | 序列号是可靠传输的基础，必须双方确认 |

> 典型场景：客户端发出的 SYN 因网络延迟滞留，客户端超时重传并完成连接后关闭。滞留的 SYN 才到达服务端，若只有两次握手，服务端直接建立连接并分配资源，但客户端已关闭，服务端资源被白白占用。

### 四次挥手

```
┌──────────────────────────────────────────────────────────┐
│              TCP 四次挥手 (Four-way Handshake)             │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  Client                         Server                   │
│    │                               │                     │
│    │  ① FIN, seq=u                 │  (主动关闭方)        │
│    │ ─────────────────────────────▶│  FIN_WAIT_1         │
│    │                               │                     │
│    │  ② ACK, ack=u+1               │                     │
│    │ ◀─────────────────────────────│  CLOSE_WAIT         │
│    │  FIN_WAIT_2                   │  (被动方可能还有数据) │
│    │                               │                     │
│    │  ③ FIN, seq=w                 │                     │
│    │ ◀─────────────────────────────│  LAST_ACK           │
│    │                               │                     │
│    │  ④ ACK, ack=w+1               │                     │
│    │ ─────────────────────────────▶│  CLOSED             │
│    │  TIME_WAIT (2MSL)             │                     │
│    │  ──▶ CLOSED                   │                     │
│                                                          │
│  为什么是四次:                                            │
│  ├── TCP 是全双工，每个方向需单独关闭                      │
│  ├── 被动方 ACK 与 FIN 不能合并 (可能还有数据未发完)       │
│  └── TIME_WAIT = 2MSL 保证最后 ACK 可达 + 消耗旧报文      │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 面试答法

> "三次握手：第一次客户端发 SYN 同步序列号，第二次服务端回 SYN+ACK 确认并同步自己的序列号，第三次客户端发 ACK 确认。核心目的是双方确认彼此的收发能力并交换初始序列号。不能两次是因为要防止历史连接请求、双方都要确认能力。四次挥手因为 TCP 全双工，被动方收到 FIN 后可能还有数据要发，所以 ACK 和 FIN 分开，形成四次。主动关闭方最后会进入 TIME_WAIT 等待 2MSL。"

## Q2: TCP 如何保证可靠传输？滑动窗口？流量控制？拥塞控制？（高频）

### 可靠传输机制总览

```
┌──────────────────────────────────────────────────────────┐
│              TCP 可靠传输四大机制                           │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  1. 校验和 (Checksum)                                    │
│     └── 检测数据是否损坏，损坏则丢弃                      │
│                                                          │
│  2. 序列号 + 确认应答 (Seq + ACK)                        │
│     └── 每个字节都有序号，ACK 表示「下一个期望的字节」    │
│                                                          │
│  3. 超时重传 (RTO)                                       │
│     └── 超时未收到 ACK → 重传该报文                       │
│     └── RTO 动态计算 (RTT 加权平滑)                      │
│                                                          │
│  4. 滑动窗口 + 流量控制 + 拥塞控制                        │
│     └── 兼顾可靠性与吞吐量                               │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 滑动窗口

```
┌──────────────────────────────────────────────────────────┐
│              滑动窗口 (Sliding Window)                     │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  发送窗口 (SND.WND):                                     │
│  ┌──────────┬─────────────┬──────────────┬────────────┐  │
│  │ 已发送   │ 可发送       │ 不可发送      │            │  │
│  │ 已确认   │ (窗口内)     │ (窗口外)      │            │  │
│  └──────────┴─────────────┴──────────────┴────────────┘  │
│           ▲           ▲                                  │
│           │           └── SND.UNA + SND.WND              │
│           └── SND.UNA (最早未确认)                        │
│                                                          │
│  特点:                                                   │
│  ├── 窗口内可连续发送多个报文，无需逐个等待 ACK           │
│  ├── 收到 ACK 后窗口右移，腾出新发送空间                  │
│  ├── 窗口大小由接收方通告 (rwnd) 动态调整                 │
│  └── 提高吞吐 + 实现流量控制                              │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 流量控制 vs 拥塞控制

| 维度 | 流量控制 | 拥塞控制 |
|------|----------|----------|
| 目的 | 防止发送方压垮接收方 | 防止发送方压垮网络 |
| 依据 | 接收方通告窗口 rwnd | 网络拥塞程度 cwnd |
| 范围 | 端到端（两点之间） | 全局（整个网络） |
| 手段 | 滑动窗口、零窗口探测 | 慢启动、拥塞避免、快重传、快恢复 |

### 拥塞控制过程

```
┌──────────────────────────────────────────────────────────┐
│              拥塞窗口 cwnd 变化                            │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  cwnd                                                      │
│   ▲          拥塞避免 (线性)                              │
│   │         ╱─────────────── 阈值 ssthresh                │
│   │        ╱                  │                            │
│   │       ╱                   │                            │
│   │      ╱   慢启动 (指数)    │                            │
│   │     ╱                     │                            │
│   │    ╱                      │                            │
│   │   ╱                       │                            │
│   │  ╱                        │                            │
│   │ ╱                         │                            │
│   │╱                          │                            │
│   └───────────────────────────┴──────────▶ 时间            │
│                                                          │
│  发生丢包:                                                │
│  ├── 超时: ssthresh = cwnd/2, cwnd = 1, 重新慢启动        │
│  └── 3 个冗余 ACK: ssthresh = cwnd/2, cwnd = ssthresh     │
│      (快恢复，不从 1 开始)                                 │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 面试答法

> "TCP 通过四层机制保证可靠：校验和检测损坏、序列号+确认应答保证有序完整、超时重传应对丢包、滑动窗口兼顾吞吐。流量控制用接收方通告的 rwnd 防止压垮接收方；拥塞控制用 cwnd 防止压垮网络，包含慢启动指数增长、拥塞避免线性增长，丢包时超时则 cwnd 置 1，三个冗余 ACK 则走快恢复。最终发送窗口取 min(rwnd, cwnd)。"

## Q3: TIME_WAIT / CLOSE_WAIT 作用与大量出现排查？

### 状态定义

| 状态 | 角色 | 何时进入 | 何时离开 |
|------|------|----------|----------|
| TIME_WAIT | 主动关闭方 | 发出最后 ACK 后 | 等待 2MSL 后自动 CLOSED |
| CLOSE_WAIT | 被动关闭方 | 收到对端 FIN、发出 ACK 后 | 本端应用 close()、发出自己的 FIN 后 → LAST_ACK |

### 为什么需要 TIME_WAIT？

```
┌──────────────────────────────────────────────────────────┐
│              TIME_WAIT 存在的意义 (2MSL)                   │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  1. 保证最后的 ACK 可达                                    │
│     └── 若 ACK 丢失，对端会重发 FIN，TIME_WAIT 内可重发    │
│                                                          │
│  2. 让旧连接的报文在网络中消散                             │
│     └── 2MSL 后，本连接的所有报文都已失效                  │
│     └── 防止相同四元组的新连接收到旧数据                  │
│                                                          │
│  3. MSL = Maximum Segment Lifetime (通常 30s / 60s)       │
│     └── TIME_WAIT = 2 * MSL = 60s (Linux 默认)            │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 大量出现的排查与处理

| 现象 | 可能原因 | 处理方式 |
|------|----------|----------|
| 大量 TIME_WAIT | 短连接、QPS 高、客户端主动关闭 | 连接池复用、HTTP Keep-Alive、长连接 |
| 大量 CLOSE_WAIT | **应用代码没 close()** / 线程卡住 | 检查代码资源释放、线程池、依赖超时 |
| 端口耗尽 | TIME_WAIT 过多导致 ephemeral port 不足 | 调大 `ip_local_port_range`、复用连接 |

```bash
# 查看各状态连接数
ss -ant | awk '{print $1}' | sort | uniq -c | sort -rn

# 查看大量 CLOSE_WAIT 的进程
ss -antp | grep CLOSE_WAIT

# 调优参数 (Linux)
# 缩短 FIN_WAIT_2 超时、开启 tw_reuse (谨慎)
net.ipv4.tcp_tw_reuse = 1
net.ipv4.ip_local_port_range = 1024 65000
```

### 面试答法

> "TIME_WAIT 是主动关闭方在发完最后 ACK 后等待 2MSL 的状态，作用是保证 ACK 可达、让旧报文消散。短连接高并发场景容易堆积，解决办法是连接复用。CLOSE_WAIT 是被动关闭方收到 FIN 后的状态，大量出现说明应用没有正确 close 连接，是代码 bug 或线程阻塞，要从资源释放查起。"

## Q4: HTTP 1.0/1.1/2/3 区别？（高频）

| 特性 | HTTP/1.0 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|------|----------|----------|--------|--------|
| 连接 | 短连接 | 默认 Keep-Alive | 多路复用 | 多路复用 |
| 队头阻塞 | 有 | 有（应用层） | 应用层无，TCP 层仍有 | 基本无（QUIC/UDP） |
| 头部 | 不压缩 | 不压缩 | HPACK 压缩 | QPACK 压缩 |
| 服务器推送 | 无 | 无 | 支持 Server Push | 支持 |
| 二进制 | 文本 | 文本 | 二进制帧 | 二进制帧 |
| 底层 | TCP | TCP | TCP | QUIC (UDP) |
| 并行 | 不支持 | 有限（多连接） | 单连接多 stream | 单连接多 stream |

```
┌──────────────────────────────────────────────────────────┐
│              HTTP/2 多路复用示意                           │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  HTTP/1.1 (串行/多连接):                                 │
│  请求A ──▶ 响应A ──▶ 请求B ──▶ 响应B                     │
│  (队头阻塞: B 必须等 A 完成)                              │
│                                                          │
│  HTTP/2 (单连接多 stream):                               │
│  ┌─── stream1: 请求A ──▶ 响应A                           │
│  │                                                       │
│  ├─── stream2: 请求B ──▶ 响应B                           │
│  └── 同一 TCP 连接，帧交错传输，互不阻塞                  │
│                                                          │
│  帧结构: [Length][Type][Flags][Stream ID][Payload]        │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 面试答法

> "HTTP/1.1 相比 1.0 默认长连接、支持分块传输和 Host 头。HTTP/2 引入多路复用、头部压缩、二进制分帧、服务器推送，解决应用层队头阻塞。但 HTTP/2 仍基于 TCP，丢包时整个连接受阻。HTTP/3 基于 QUIC/UDP，实现流级重传和 0-RTT 建连，彻底解决传输层队头阻塞，移动网络切换场景延迟更低。"

## Q5: HTTPS 握手过程？对称/非对称加密？证书？（高频）

### 对称 vs 非对称加密

| 维度 | 对称加密 | 非对称加密 |
|------|----------|------------|
| 密钥 | 加解密同一把（AES） | 公钥加密、私钥解密（RSA/ECC） |
| 速度 | 快 | 慢（约慢 100 倍以上） |
| 安全分发 | 难（密钥如何安全传输？） | 公钥可公开 |
| HTTPS 中用途 | 通信内容加密（会话密钥） | 密钥交换 / 数字签名 |

### HTTPS/TLS 握手（TLS 1.2 简化流程）

```
┌──────────────────────────────────────────────────────────┐
│              HTTPS 握手过程 (TLS 1.2)                     │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  Client                                  Server          │
│    │                                        │            │
│    │ ① Client Hello (支持的加密套件、随机数) │            │
│    │ ──────────────────────────────────────▶│            │
│    │                                        │            │
│    │ ② Server Hello (选定套件、随机数)      │            │
│    │    + 证书 (公钥) + Server Hello Done   │            │
│    │ ◀──────────────────────────────────────│            │
│    │                                        │            │
│    │ ③ 验证证书 → 生成预主密钥 (Pre-Master) │            │
│    │    用服务器公钥加密后发送               │            │
│    │ ──────────────────────────────────────▶│            │
│    │                                        │            │
│    │ ④ 双方用「随机数 + Pre-Master」        │            │
│    │    派生出会话密钥 (对称密钥)            │            │
│    │    Change Cipher Spec + Finished       │            │
│    │ ◀─────────────────────────────────────▶│            │
│    │                                        │            │
│    │ ⑤ 之后用对称加密通信 (AES-GCM 等)      │            │
│    │                                        │            │
│  核心思想: 非对称加密安全分发密钥，对称加密高效传数据     │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 数字证书作用

```
┌──────────────────────────────────────────────────────────┐
│              证书信任链                                    │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  证书内容:                                                │
│  ├── 服务器域名 (CN/SAN)                                 │
│  ├── 服务器公钥                                          │
│  ├── 有效期                                              │
│  ├── 颁发者信息                                          │
│  └── CA 的数字签名 (用 CA 私钥签)                        │
│                                                          │
│  验证过程:                                                │
│  ├── 1. 浏览器用 CA 公钥解密签名 → 得到摘要               │
│  ├── 2. 自己对证书内容哈希 → 对比摘要                     │
│  ├── 3. 检查域名、有效期、是否吊销 (CRL/OCSP)            │
│  └── 4. 沿证书链上溯到内置根 CA                          │
│                                                          │
│  作用: 防止中间人伪造公钥 (MITM)                          │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 面试答法

> "HTTPS = HTTP + TLS。核心是混合加密：非对称加密（RSA/ECDHE）安全交换密钥，对称加密（AES）高效传输数据。客户端验证服务器数字证书，确认公钥归属，防止中间人。TLS 1.2 两个 RTT 建连，TLS 1.3 一个 RTT，支持 0-RTT。证书由 CA 签发，浏览器内置根 CA 信任链验证。"

## Q6: HTTP 常见状态码？301/302/304/401/403/500/502/504？

| 状态码 | 含义 | 典型场景 |
|--------|------|----------|
| 200 | OK 成功 | 正常响应 |
| 204 | No Content | 成功但无响应体 |
| 206 | Partial Content | Range 断点续传 |
| **301** | Moved Permanently | 域名永久迁移，浏览器/搜索引擎更新 URL |
| **302** | Found（临时重定向） | 登录后跳转首页 |
| 303 | See Other | POST 后重定向到 GET 结果页 |
| **304** | Not Modified | 协商缓存命中，无需重传资源 |
| 307 | Temporary Redirect | 临时重定向，保留请求方法 |
| **400** | Bad Request | 参数错误、JSON 格式非法 |
| **401** | Unauthorized | 未登录/Token 无效，需身份认证 |
| **403** | Forbidden | 已登录但无权限访问该资源 |
| 404 | Not Found | 资源不存在 |
| 405 | Method Not Allowed | 方法不被允许 |
| 429 | Too Many Requests | 触发限流 |
| **500** | Internal Server Error | 服务端代码异常 |
| **502** | Bad Gateway | 网关/代理从上游收到无效响应（上游挂了） |
| **503** | Service Unavailable | 服务暂时不可用（过载/维护） |
| **504** | Gateway Timeout | 网关等待上游超时 |

### 301 vs 302、401 vs 403、502 vs 504 对比

| 对比 | 差异 |
|------|------|
| 301 vs 302 | 301 永久迁移（可缓存、换域名用），302 临时（不可缓存） |
| 302 vs 307 | 307 保证重定向后仍是原方法（POST 不会变 GET） |
| 401 vs 403 | 401 未认证（登录），403 已认证无权限（鉴权） |
| 500 vs 502 vs 504 | 500 本服务异常；502 上游无效响应；504 上游超时 |

### 面试答法

> "301/302 是重定向，301 永久、302 临时。304 是协商缓存命中。401 是未认证，403 是无权限。500 是服务端异常，502 是网关收到上游无效响应（上游实例挂了），504 是网关等待上游超时。排查 502/504 通常看网关到上游服务的健康状态、超时配置和连接数。"

## Q7: Cookie / Session / Token / JWT 区别？（高频）

| 维度 | Cookie | Session | Token (Opaque) | JWT |
|------|--------|---------|----------------|-----|
| 存放位置 | 浏览器 | 服务端 (内存/Redis) | 客户端（可存 Cookie/LocalStorage） | 客户端 |
| 安全性 | 易被截获/CSRF | 相对安全 | 较高（可 HttpOnly） | 需防 XSS，签名防篡改 |
| 服务端压力 | 无状态存储 | 有状态，需共享存储 | 可查库/Redis 校验 | 无状态，本地校验 |
| 分布式 | 天然支持 | 需 Session 共享/粘性 | 易扩展 | 天然适合微服务 |
| 大小限制 | 4KB 左右 | 无固定限制 | 视实现 | Header 大小限制 |
| 注销/踢下线 | 可清 Cookie | 直接删 Session | 删除/黑名单 | 较难（靠短过期+刷新） |
| 跨域 | SameSite 限制 | 依赖 Cookie 传递 | 灵活 | 灵活 |

### Session 原理与共享问题

```
┌──────────────────────────────────────────────────────────┐
│              Session 共享方案                              │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  问题: 多实例部署时 Session 不同步                         │
│                                                          │
│  方案一: Redis 集中存储 (主流)                            │
│  ┌─────────────────────────────────────────────────┐     │
│  │  Spring Session + Redis                          │     │
│  │  所有实例读写同一 Redis，SESSION_ID 由 Cookie 带 │     │
│  └─────────────────────────────────────────────────┘     │
│                                                          │
│  方案二: 粘性 Session (IP Hash)                           │
│  └── 负载均衡按 IP 固定到同一实例，重启失效               │
│                                                          │
│  方案三: Token / JWT (无状态)                            │
│  └── 服务端不存会话，每次请求携带 Token 验证              │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### JWT 结构

```text
JWT = Header.Payload.Signature

Header:  {"alg":"HS256","typ":"JWT"}
Payload: {"sub":"1001","name":"张三","exp":1735689600,"roles":["admin"]}
Signature: HMACSHA256(base64(Header)+"."+base64(Payload), secret)

传输形态: Authorization: Bearer <token>
```

### 面试答法

> "Cookie 存浏览器、大小 4KB，适合存会话 ID；Session 存服务端，分布式要共享到 Redis（Spring Session）；Token 是无状态凭证，服务端可存黑名单；JWT 是自包含 Token，Header.Payload.Signature，服务端用密钥验签即可，适合微服务无状态认证。JWT 缺点是注销难、Payload 只是 Base64 不是加密、体积偏大。生产常用：短效 JWT + Refresh Token + 黑名单踢人。"

## Q8: 从浏览器输入 URL 到页面展示发生了什么？（高频综合题）

```
┌──────────────────────────────────────────────────────────┐
│          URL → 页面展示 完整链路                           │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  1. URL 解析                                              │
│     └── 浏览器缓存/历史补全，判断是搜索还是 URL            │
│                                                          │
│  2. DNS 解析 (域名 → IP)                                 │
│     ├── 浏览器缓存 → OS 缓存 → hosts → 本地 DNS           │
│     ├── 递归 DNS: 根 → 顶级域 → 权威 DNS                 │
│     └── 结果缓存 (TTL)                                    │
│                                                          │
│  3. 建立 TCP 连接 (HTTPS 则还有 TLS 握手)                 │
│     └── 三次握手 / 2-RTT (TLS1.2) 或 1-RTT (TLS1.3)     │
│                                                          │
│  4. 发送 HTTP 请求                                        │
│     └── GET /index.html  Host: example.com               │
│                                                          │
│  5. 服务器处理并返回响应                                  │
│     └── Nginx → 应用服务 → 数据库/缓存                   │
│     └── 状态码 + 响应头 + 响应体 (HTML)                   │
│                                                          │
│  6. 浏览器解析渲染                                        │
│     ├── 解析 HTML → 构建 DOM 树                          │
│     ├── 解析 CSS  → 构建 CSSOM                           │
│     ├── DOM + CSSOM → Render Tree → Layout → Paint       │
│     ├── 遇到 <script> 可能阻塞解析 (同步)                │
│     └── 图片/字体等子资源继续加载，触发重绘回流           │
│                                                          │
│  7. 四次挥手断开 (或 Keep-Alive 复用)                     │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 面试答法

> "分七步：DNS 解析拿到 IP；TCP 三次握手，HTTPS 再加 TLS 握手；发 HTTP 请求；服务端处理返回 HTML；浏览器解析 HTML 构建 DOM，解析 CSS 构建 CSSOM，合成渲染树后 Layout、Paint；子资源加载可能触发重绘；最后连接关闭或复用。加分点可提：DNS 负载均衡、CDN、HTTP 缓存（强缓存/协商缓存）、关键渲染路径、script 阻塞、预解析 dns-prefetch。"

## Q9: 跨域问题与解决方案？CORS？

### 为什么会有跨域？

```
┌──────────────────────────────────────────────────────────┐
│              同源策略 (Same-Origin Policy)                 │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  同源 = 协议 + 域名 + 端口 三者完全一致                    │
│                                                          │
│  http://www.example.com:8080/index.html                  │
│  └── 协议 http、主机 www.example.com、端口 8080           │
│                                                          │
│  跨域示例:                                                │
│  ├── http://www.example.com  vs https://www.example.com  │
│  ├── http://www.example.com  vs http://api.example.com   │
│  └── http://www.example.com:8080 vs :8081                │
│                                                          │
│  限制对象: XHR / Fetch 跨域读响应、Cookie 等               │
│  不受限:   <script> <img> <link> 加载、表单提交            │
│  根本原因: 浏览器安全策略，服务端本身不阻止跨域            │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 解决方案对比

| 方案 | 原理 | 适用场景 | 注意 |
|------|------|----------|------|
| **CORS** | 服务端返回 Access-Control-* 头 | 最主流的前后端分离 | 配置可信 Origin |
| Nginx 反向代理 | 同源到 Nginx，由 Nginx 转发 API | 开发/生产均可 | 无跨域，最干净 |
| WebSocket | 不受同源策略限制 | 实时通信 | 协议不同 |
| JSONP | script 标签跨域加载 | 仅 GET，已过时 | 有安全风险 |
| postMessage | window 间通信 | iframe 嵌套 | 仅通信场景 |

### CORS 关键头与预检

```
┌──────────────────────────────────────────────────────────┐
│              CORS 请求流程                                │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  简单请求 (GET/POST 无自定义头):                          │
│  ├── 请求带 Origin: http://www.example.com               │
│  └── 响应: Access-Control-Allow-Origin: ...              │
│                                                          │
│  预检请求 (复杂请求):                                     │
│  ├── ① OPTIONS 预检                                      │
│  │   Access-Control-Request-Method: PUT                  │
│  │   Access-Control-Request-Headers: Content-Type        │
│  │                                                       │
│  │   响应:                                                │
│  │   Access-Control-Allow-Origin: http://www.example.com │
│  │   Access-Control-Allow-Methods: GET, POST, PUT        │
│  │   Access-Control-Allow-Headers: Content-Type          │
│  │   Access-Control-Max-Age: 86400                       │
│  │                                                       │
│  └── ② 预检通过 → 发送真正请求                           │
│                                                          │
│  携带 Cookie:                                             │
│  ├── 前端: fetch(url, { credentials: 'include' })        │
│  └── 服务端: Access-Control-Allow-Credentials: true      │
│              Access-Control-Allow-Origin 不能是 *        │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### Spring Boot 配置 CORS 示例

```java
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("https://www.example.com")
                .allowedMethods("GET", "POST", "PUT", "DELETE")
                .allowedHeaders("*")
                .allowCredentials(true)
                .maxAge(3600);
    }
}
```

### 面试答法

> "跨域是浏览器同源策略导致的，协议+域名+端口不一致就跨域，服务端本身并不禁止。主流方案是 CORS：简单请求直接带 Origin，复杂请求先 OPTIONS 预检，服务端返回 Access-Control-Allow-* 头。生产更推荐 Nginx 反向代理消除跨域。注意携带 Cookie 时 Allow-Origin 不能是 *，必须指定具体域名并开 Credentials。"

## 面试答法总结

> "计算机网络高频考点集中在三块：TCP 连接管理（三次握手/四次挥手/状态排查）、可靠传输（窗口/流控/拥塞）、HTTP 演进与安全（1.1/2/3、HTTPS、鉴权、跨域）。答网络题时先给结论再展开机制，结合场景（短连接、移动端、微服务鉴权）会更分。"

### 高频追问速查

| 追问 | 关键点 |
|------|--------|
| 为什么不是两次握手？ | 防历史连接 + 双方确认收发能力 |
| TIME_WAIT 过多？ | 连接复用、Keep-Alive、tw_reuse |
| CLOSE_WAIT 过多？ | 应用未 close，查代码/线程 |
| HTTP/2 为何还阻塞？ | TCP 层队头阻塞，丢包影响整连接 |
| HTTP/3 为何快？ | QUIC、流级重传、0-RTT、连接迁移 |
| JWT 如何注销？ | 短过期 + Refresh Token + 黑名单 |
| 502 与 504？ | 502 上游无效，504 上游超时 |
